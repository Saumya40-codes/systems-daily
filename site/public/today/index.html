SQLite WAL checkpoint starvation: one old reader holds the line

A reader fixes the version it is allowed to see

In SQLite WAL mode, a read transaction starts by fixing an end mark: the last valid commit visible at the moment the transaction begins. From then on, page lookup is constrained by that snapshot. If the same database page has several versions in the WAL, the reader uses the last frame for that page at or before its end mark. It does not advance to frames committed later by other connections. [1]

That snapshot rule is what lets old readers coexist with new writes. Writers can continue by appending committed frames to the WAL while an existing reader keeps using its earlier view. SQLite WAL mode permits concurrent readers with one writer, so a reader pinned to an old snapshot does not by itself prevent later commits from being appended. [1]

time ---->

WAL frames:
[1] [2] ... [900] | [901] [902] ... [5000]
                 ^
                 reader R starts here
                 high-level end mark = last commit visible to R

reader R page lookup:
  page P -> newest WAL frame for P at or before frame 900

writers:
  append committed frames after frame 900

The tension is not on the write path. It appears on the cleanup path. A checkpoint tries to copy WAL frames back into the main database, but it must not move past the boundary needed by any active reader. Otherwise a reader that started at an older snapshot could no longer reconstruct the page versions it is allowed to see. [1]

Checkpoint progress is bounded by active readers

A checkpoint can still do useful work while readers exist. The failure mode is partial checkpointing, not necessarily no checkpointing. It may backfill frames that are safe for all active readers, then stop when further progress would pass a protected reader boundary. Long-lived or overlapping readers can therefore prevent a checkpoint from completing and resetting the WAL. [1]

The distinction between “complete” and “made progress” matters. If a checkpoint copies some older frames but cannot reach the current end of committed WAL content, the WAL remains in use. New commits can continue appending after the portion the checkpoint could not finish, so the WAL file can keep growing even though checkpoint attempts are occurring. [1]

checkpoint direction ---->

WAL:
[1] [2] ... [900] | [901] [902] ... [5000]
                 ^
                 active reader's protected checkpoint boundary

checkpoint:
  backfills eligible earlier frames
  stops before passing the active reader boundary

result:
  checkpoint incomplete
  WAL cannot reset
  later writes append more frames

The wal-index adds coordination state

The WAL overview describes the reader’s high-level end mark. The WAL-format layer exposes the coordination machinery used to make this efficient and safe. The wal-index is shared memory that lets SQLite locate the newest acceptable WAL frame for a page without scanning the whole WAL. It also holds checkpoint-related state, including `mxFrame`, `nBackfill`, read marks, and locks. [2]

`mxFrame` is the last valid committed WAL frame. `nBackfill` counts frames already copied from the WAL into the database. A WAL reset is possible when `nBackfill == mxFrame` and no connection holds `WAL_READ_LOCK(N)` for `N > 0`. If an active reader prevents backfill from reaching `mxFrame`, that reset condition is not reached. [2]

Do not collapse the high-level end mark and the wal-index read mark into one field. The WAL header has five read marks. A reader holding `WAL_READ_LOCK(N)` promises how it will obtain pages relative to `read-mark[N]`, and a checkpoint must not backfill more than that read mark. For `N > 0`, the same reader may still use WAL content beyond `read-mark[N]` up to its transaction’s `mxFrame`. The read mark is a checkpoint coordination boundary, not simply another name for the reader’s snapshot end mark. [2]

The locks separate checkpoint and write serialization. `WAL_CKPT_LOCK` serializes checkpoints. `WAL_WRITE_LOCK` serializes appends and resets. That is why a system can still append new WAL frames while checkpoint completion and reset remain constrained by reader state. [2]

A concrete starvation trace

Suppose the WAL has 900 committed frames. Reader R starts a transaction, fixing its snapshot at that point. Writers then commit more transactions and append frames 901 through 5000. In this example, `mxFrame` is now 5000, because that is the last valid committed WAL frame. [1] [2]

initial:
  committed WAL frames = 1..900
  reader R starts
  R sees commits through frame 900

after more writes:
  committed WAL frames = 1..5000
  mxFrame = 5000
  R still reads from its older snapshot

checkpoint attempt:
  nBackfill advances only as far as active reader constraints allow
  checkpoint cannot complete through mxFrame

reset test:
  nBackfill == mxFrame ?  no
  no nonzero WAL_READ_LOCK(N)?  no, while such a reader lock remains

outcome:
  WAL reset is not possible
  later commits append after frame 5000

SQLite’s default automatic checkpoint threshold is around 1000 WAL pages, so the system may start checkpointing as the WAL grows. That does not guarantee reset. A `PASSIVE` checkpoint does as much work as possible without interfering with concurrent connections and may not complete. `FULL` and `RESTART` try harder and may wait for readers or writers, but they still operate under the reader and lock constraints that determine whether the checkpoint can finish. [1]

This is checkpoint starvation in the narrow sense: writes are not necessarily starved, but checkpoint completion is. One old reader keeps enough WAL history live for its snapshot. While that reader remains active, `nBackfill` may be unable to catch `mxFrame`; if new commits continue, `mxFrame` moves forward again. After the reader is gone, a later checkpoint may be able to backfill through `mxFrame`, clear the reset conditions, and allow the WAL to reset, provided no other active reader is holding a conflicting boundary. [2]
